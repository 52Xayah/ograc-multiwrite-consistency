# oGRAC 双节点多写一致性实验结果

## 1. 实验概述

本实验基于 oGRAC 双节点集群，通过两个独立数据库会话分别连接 Node0 和 Node1，完成 DDL、DML 及跨节点并发更新验证。

三个实验均按照预定步骤完成，实际执行现象与预期一致。

| 实验项目 | 验证内容 | 实验结果 |
|:---|:---|:---:|
| DDL 同步验证 | 跨节点数据库对象可见性 | 通过 |
| DML 同步验证 | 跨节点数据读写可见性 | 通过 |
| 并发更新验证 | 行锁等待与事务提交行为 | 通过 |

## 2. 实验一：跨节点 DDL 可见性

### 实验结果

按照 Node0 创建、Node1 重复创建、Node0 删除、Node1 重新创建的顺序执行操作，结果如下：

| 操作 | 实际结果 |
|:---|:---|
| Node0 创建 `test_mulNode` | 执行成功 |
| Node1 创建同名表 | 执行失败，提示表已存在 |
| Node0 删除测试表 | 执行成功 |
| Node1 再次创建同名表 | 执行成功 |
| Node1 插入并查询数据 | 执行成功，能够正常读取测试数据 |

### 结果分析

Node0 创建测试表后，Node1 能够感知该表已经存在，重复创建操作返回预期错误。

当 Node0 删除测试表后，Node1 又能够成功创建同名表。

这一过程说明，在本次实验环境和操作场景下，数据库对象的创建与删除变更能够被另一个节点观察到，体现了双节点环境下 DDL 操作的跨节点可见性。

### 实验结论

DDL 操作在两个节点之间具有预期的可见性。一个节点完成的表结构变更能够影响另一个节点后续对同名数据库对象的操作。

## 3. 实验二：跨节点 DML 可见性

### 实验结果

按照 Node0 初始化数据、Node1 更新数据、Node0 再次查询的顺序执行操作，结果如下：

| 操作 | 实际结果 |
|:---|:---|
| Node0 创建测试表并初始化数据 | 成功插入三条记录 |
| Node0 查询 `c1 = 1` | 初始值 `c3 = 11` |
| Node1 更新目标记录 | 更新成功，`c3` 修改为 77 |
| Node0 再次查询 | 成功读取到 `c3 = 77` |

关键更新语句：

```sql
UPDATE test_mulNode
SET c3 = 77
WHERE c1 = 1;
```

### 结果分析

实验中，Node0 负责初始化数据，Node1 对其中一条记录执行更新，随后 Node0 再次查询该记录。

Node0 最终读取到更新后的值 77，说明 Node1 完成的修改在提交后能够被 Node0 观察到。

由于两个会话均采用自动提交方式，本实验验证的是已提交数据的跨节点可见性，不涉及未提交数据的读取。

### 实验结论

在本次测试场景下，两个节点均能够参与同一份数据的读写操作。一个节点提交的数据修改能够被另一个节点查询到，验证了跨节点 DML 可见性。

## 4. 实验三：跨节点同一行并发更新

### 实验结果

本实验通过两个独立会话关闭自动提交，控制两个事务对同一行数据的更新顺序。

| 步骤 | Node0（会话 A） | Node1（会话 B） | 实际现象 |
|:---:|:---|:---|:---|
| 1 | 更新目标记录为 55，不提交 | — | 更新成功，事务保持未提交 |
| 2 | — | 更新同一记录为 66 | 操作进入等待状态 |
| 3 | 执行 `COMMIT` | 等待中的更新继续执行 | Node0 提交后，Node1 恢复执行 |
| 4 | — | 执行 `COMMIT` | Node1 提交成功 |
| 5 | 查询目标记录 | — | 最终 `c3 = 66` |

关键 SQL：

```sql
-- Node0：更新后暂不提交
UPDATE test_mulNode
SET c3 = 55
WHERE c1 = 4;

-- Node1：更新同一行
UPDATE test_mulNode
SET c3 = 66
WHERE c1 = 4;
```

### 结果分析

实验过程中，Node0 首先更新目标记录，但没有立即提交事务。

此时 Node0 的事务仍然持有相关行锁。Node1 随后尝试更新同一条记录，由于发生写写冲突，操作进入等待状态。

当 Node0 执行 `COMMIT` 后，事务结束并释放相关锁，Node1 的更新操作随之继续执行并成功返回。

最后，Node1 提交事务，查询目标记录得到 `c3 = 66`。

这一过程体现了以下几个重要现象：

1. 事务执行更新后，即使 SQL 已经返回，未提交事务仍可能持有行锁。
2. 不同节点对同一行进行并发写入时，需要协调锁冲突。
3. 前一个事务提交后，等待中的事务才能继续执行。
4. 最终数据由后续成功提交的更新决定。

### 实验结论

在本次并发更新场景下，oGRAC 能够协调不同节点对同一行数据的写操作。当一个事务持有目标行锁时，另一个节点的冲突更新进入等待；前一个事务提交后，等待操作继续执行。

最终数据为 66，与预期一致。

## 5. 综合实验结论

通过三个实验，从数据库对象、数据记录和事务并发三个层面验证了 oGRAC 双节点环境下的多写行为。

| 验证维度 | 实验现象 | 验证结论 |
|:---|:---|:---|
| DDL 可见性 | 一个节点创建或删除表后，另一个节点能够感知变化 | DDL 变更具有跨节点可见性 |
| DML 可见性 | 一个节点提交更新后，另一个节点能够读取新值 | 已提交数据具有跨节点可见性 |
| 并发写入 | 同一行发生写写冲突时，后发起的更新进入等待 | 存在跨节点事务锁协调行为 |

本次实验表明，oGRAC 双节点环境能够支持不同节点参与数据库读写操作，并在测试场景下保持预期的数据可见性和事务执行顺序。

通过实际操作，也进一步理解了数据库事务提交、行级锁和并发写入之间的关系。

## 6. 实验限制与后续改进

当前实验主要覆盖双节点环境下的 DDL、DML 和同一行写写冲突，尚未涉及以下场景：

- 事务回滚对等待事务的影响。
- 不同行数据的并发更新。
- 锁等待超时与死锁处理。
- 不同事务隔离级别下的数据读取行为。
- 节点故障、网络异常及恢复。
- 多节点读写性能与扩展性测试。

后续可以在现有实验基础上，增加回滚、不同数据行并发更新等对照实验，进一步分析多节点事务协调机制。
